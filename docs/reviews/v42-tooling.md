# v42 tooling and architecture review

9 November 2026. Source review of the current v41 application, retained native studies, and current primary upstream documentation. This reviewer made no product edits or deployment and performed no project execution, dependency installation, scientific run, VM creation/synchronization/deletion, or browser interaction. Root separately ran fresh isolated checks and CPU probes; their reopened logs are explicitly attributed below. Reading a retained native result is evidence of a recorded calculation, not an independent rerun.

## Assessment

The scientific stack is real and reasonably chosen. The interactive application runs custom TypeScript numerical models; Julia, PETSc, WarpX, FiPy, RustBCA, OpenMC and NJOY are offline study/reference tools. Those names should not imply that an arbitrary live result is produced or physically qualified by those packages. The present product usually distinguishes these roles correctly. The strongest next work is qualified coverage and removing unnecessary work from the interaction path, not adopting more languages/frameworks.

Three.js/Blender/glTF, cancellable browser workers and compact recorded response tables remain suitable. React, React Three Fiber, WebGPU compute, a Julia service, or another plotting library would not by themselves supply measured material coefficients, reaction rates, valid collision domains, or deployed-browser evidence. The existing source-linked geometry, batched fields and exact cell inspection are substantive improvements since v37; the old review's assertion that sliders never change the hardware is no longer current.

## Demonstrated execution issues and operational risk

### T42-1 — P2 efficiency follow-up: collapsed references still calculate synchronously on every source edit

**Verified path:** source range `input` directly calls `update` (`fusion-ui.js:82`). That invokes the live initial slab plus a 25–26-energy scan (`fusion-ui.js:35–38`; `fusion-playground.ts:7–14`), renders plots, then calls the Marathon fanout. `marathon-ui.js:41–42` synchronously updates geometry, legacy bulk exposure and legacy loading before scheduling the coupled-target worker. The legacy models were explicitly moved into the target reference host (`:39`). `target-loading-ui.js:28–29` performs two adaptive loading runs, at the selected tolerance and one tenth of it, whether its details panel is open or closed. `target-exposure-ui.js:35–46` also calculates and redraws its collapsed reference. Only extra ledger curves are visibility-gated.

**Problem:** the cancellable worker does not isolate all source-edit work. Closed historical references and sensitivity curves still calculate/redraw for every drag event. This is unnecessary work, not a demonstrated perceptible-latency defect. Root's fresh isolated Node CPU witness (`scientific/audit-v42/numerical-witness.log`) is small at tested default source settings: six trials with replacement probability 0 show energy scan 0.905–4.762 ms (warm trials approximately 0.91 ms) and loading pair 0.356–1.078 ms; probability 0.5 shows scan 0.907–0.945 ms and loading pair 0.933–3.181 ms. These exclude DOM, browser frame timing and GPU work and do not establish worst-case or mobile performance. Treat this as a bounded P2 efficiency follow-up, below demonstrated correctness defects.

**Technical cause:** input notification, source recomputation and reference rendering share a synchronous fanout. The visibility boundary is applied to DOM presentation, not to calculation scheduling. The later worker's 250 ms debounce cannot cancel this earlier main-thread work.

**Simple cause:** moving old models into a closed drawer hid them without stopping their calculations.

**Preferred correction:** let reference adapters retain the latest source and mark themselves dirty while closed, then calculate once on opening/export demand. Keep the small authoritative source calculation immediate. Cache or defer the energy scan when its input identity has not changed; changing current/spot area does not necessarily require re-solving the material energy path, but that dependency should be demonstrated before adding a cache. Move an actually slow mandatory calculation into the existing worker boundary only after timing it.

**Why preferred:** this removes the demonstrated unnecessary work without changing equations, tolerances, results, or public controls. A generic scheduler, new frontend framework, parallel native service, or GPU solver adds substantially more correctness/operational work. Simply loosening loading tolerance would alter numerical behavior and would not address the cause.

**Regression/acceptance gate:** instrument numerical-call counts through a source edit with References closed: zero reference solves/redraws; opening each reference computes exactly once using the newest source. Repeated open/close without input changes reuses that snapshot. Export must use current inputs, never stale cached data. Include a preexisting retained/shared scenario and change-while-closed case. Measure input-to-paint and source-to-worker scheduling for default/material/worst allowed settings in the exact deployed browser; a desktop Node/jsdom timing is only a CPU/DOM proxy.

### T42-2 — P2: an unused legacy renderer is initialized on the default apparatus view

**Verified path:** `main.js:441` unconditionally calls `initScene()` after experience selection. Default level 1 explicitly chooses `showView('render')` (`experience-ui.js:34–38`), which uses the separate apparatus viewer. Nevertheless, `main.js:178–205` creates/initializes a WebGPURenderer, computes a PMREM environment, loads `/separator.glb`, allocates its scene, compiles it and renders once before the animation callback checks whether the legacy canvas is hidden. Research and Marathon entry also call that initialization. The apparatus viewer already uses visibility-triggered dynamic import and on-demand rendering (`apparatus-ui.js:28–42`; `apparatus-viewer.js:49–53,147`).

**Problem:** the source path requests CPU/network/GPU setup and retains a second renderer/environment for an invisible legacy scene. No actual frame latency, active-context count or VRAM was measured. Root's fresh Vite build (`scientific/audit-v42/build.log`) reports main JavaScript 1,325.94 kB minified / 385.15 kB gzip, apparatus 378.60 kB / 94.71 kB gzip, and worker 99.17 kB. These are build sizes, not measured network-transfer or responsiveness costs. The apparatus chunk imports shared symbols from the entry, so these numbers do not establish a duplicate copy of Three's core.

**Technical cause:** renderer lifetime is application-global while actual use is view-specific. The visibility guard only suppresses subsequent draws, after construction and shader/environment work have happened.

**Simple cause:** the app prepares a second 3D display even when the user is looking at the new one.

**Preferred correction:** lazily initialize the legacy scene once when a view requiring its canvas is selected; preserve current retry/failure/status behavior and existing numerical state. After this is correct, consider a dynamic import for that renderer path if an actual bundle trace shows worthwhile load savings. Keep WebGL apparatus and WebGPU-capable legacy behavior until a measured capability/compatibility need favors consolidation.

**Why preferred:** matches resource ownership to the existing view boundary and reuses the proven lazy apparatus pattern. Replacing all renderers, forcing WebGPU, or removing supported views is broader and unnecessary. Three documents automatic WebGL2 fallback, so a “WebGPU” constructor alone is neither proof of a GPU compute engine nor of actual backend usage. [Official renderer behavior](https://threejs.org/docs/pages/WebGPURenderer.html), [official resource cleanup guidance](https://threejs.org/manual/en/cleanup.html).

**Regression/acceptance gate:** injected renderer/loader factories are not invoked for the initial render/research/Marathon path; entering legacy orbit/field/hardware views initializes once and displays the latest accepted state; rapid switches, rejected initialization and retries do not attach stale scene resources. Preserve the device/backend status. Observe actual deployed GPU context creation, fetched resources, first interaction and mobile memory before claiming a measured improvement.

### T42-3 — P1 operational: unique native material evidence still depends on an unexported guest volume

**Verified evidence:** `scientific/material-v38/raw-retention.json` identifies 5,330,275,010 raw bytes in 16 cases in guest `safe-dev-91df66bcebf94022`, with exact raw hashes supplied by `readout.json`. It says host raw transport was not completed, seven archive hashes still match, two derived archives are invalid, and destructive cleanup/sync is prohibited. `docs/FINITE-FILM-V38.md:29` records the 512 MiB export cap and actual host-disk-full corruption. The independent reducer did read all native raw output; the reported scientific checks are not invalidated by the export limitation. This review has not reopened that guest, so its present raw availability is not freshly verified.

**Problem:** archived browser summaries are reproducible evidence pointers, but the authoritative raw output has a single retained operational location. Routine volume cleanup or source replacement could destroy unique results. Root confirms that cleanup intentionally preserved this exact material-v38 volume; no raw loss is established or alleged. This is an artifact-lifecycle risk, not a missing simulation library or a reason to rerun to obtain more favorable outputs.

**Technical cause:** verbose raw output exceeds the per-export boundary; attempted derived archives exceeded practical host capacity, and a complete independently verified export has not closed the ownership lifecycle.

**Simple cause:** the experiment finished, but its large original files have not finished moving to durable storage.

**Preferred correction:** before another material campaign, prepare storage and a bounded per-case/chunk transfer plan, export to a user-approved location with enough capacity, independently verify each original raw digest after extraction, and only then record an explicit owner release. Preserve the failed derived archives' status and never treat gzip creation or summary hashes as raw backup verification. No cleanup is authorized by this report.

**Why preferred:** closes the actual risk without modifying physics or discarding the records that support endpoint and energy ledgers. Upstream RustBCA offers distributions and `no_list_output` features, but choosing those solely to reduce disk would remove particle records used by the present independent audit. Evaluate compact native tallies only in a separately defined future protocol that demonstrates equivalent sufficient evidence. [RustBCA documented output options](https://github.com/lcpp-org/RustBCA#features).

**Acceptance gate:** manifest-complete raw restore in a separate location, all original file hashes verified, independent reducer reproduces the recorded public summaries, partial/corrupt/missing chunk fails closed, and guest ownership is explicitly released only after this succeeds. Check available disk against worst-case output plus transfer overhead before launches.

## Disclosed scope limitations and conditional scientific roadmap

### T42-4 — Conditional research priority: join qualified reaction/material data to observables

This is not a demonstrated correctness defect or release blocker for the disclosed scenario playground. It becomes a P1 qualification gate only if predictive isotope yield, target lifetime, shielding or whole-device performance is required. It should not be combined with T42-1/T42-2 in a bug count.

**Verified boundary:** `neutron-response.ts:28–61` intentionally admits one fixed free-H1/14.1 MeV/cylinder family. The native study tallies only `absorption` and `total` (`scientific/neutron-v38/response-study.py:43`). The interactive neutron calculation is first-flight, with scattered paths unresolved (`neutron-transport.ts:127–133`). The generic decay UI receives user rates, not reaction-resolved native transport rates. Finite-film data are 100 keV recordings and explicitly do not supply live loading kernels (`finite-film-ui.js:3–6`). These are honest boundaries, not numerical bugs. They are consequential gaps if the intended technical depth is isotope yield, target lifetime, shielding or apparatus performance.

**Technical cause:** the current integration validates separate, narrow numerical observables. There is no qualified source-spectrum → material-resolved reaction-rate → isotope inventory pipeline, nor measured kinetic/thermal coefficients for evolving LiT. A package's existence in the study folder cannot bridge those missing physical/data contracts.

**Simple cause:** the strong reference tools answer small checked questions; they do not yet answer the whole machine question.

**Preferred next scientific slice:** retain OpenMC and its successful offline-response pattern. Choose one real material/reaction and bounded source/geometry family; tally reaction-specific responses with pinned evaluated data and explicit per-source normalization; connect that result to one audited irradiation/cooldown chain. OpenMC already supports coupled and independent depletion and fixed-source normalization. Material volume, chain identity and source-rate units are actual necessary inputs. [OpenMC depletion and fixed-source transmutation](https://docs.openmc.org/en/stable/usersguide/depletion.html), [OpenMC required data](https://docs.openmc.org/en/latest/usersguide/data.html).

In parallel only if the target question demands it, extend the existing RustBCA parameter envelope and obtain defensible compound/temperature/retention data. The upstream project explicitly warns that example materials/defaults need validation. More BCA runs do not establish slow trapping, chemistry, phase stability or coolant adequacy. Extend FiPy to the new declared heat equations when measured properties/radial geometry warrant them; its existing 1D solve is already a credible oracle, and its PETSc/parallel capability is irrelevant to a 12-cell tridiagonal solve. [RustBCA material warning](https://github.com/lcpp-org/RustBCA#getting-started), [FiPy solver capabilities](https://pages.nist.gov/fipy/en/stable/SOLVERS.html).

**Why preferred:** uses the tools already producing inspected native artifacts, adds one scientifically meaningful observable, and keeps the browser immediate through qualified offline tables. A live service for every slider would add cost and state without supplying absent material evidence. A new handwritten browser multiple-scattering engine would duplicate mature cross-section/secondary/tally infrastructure. Do not relax the exact H1 family guard to make the existing table look more general.

**Acceptance gate:** source-off/decay-only and single-reaction analytic controls, reaction/atom balances, independently checked material volumes and normalization, raw tally/chain/data hashes, mesh/time/Monte Carlo refinement, held-out source/geometry conditions, and separate statistical/interpolation/model/data uncertainties. Unsupported live conditions stay explicitly outside the family. This is a new feature split, not grounds to silently change current scenario behavior.

## Physical solver bottlenecks and adoption decisions

1. **Browser thermal solve:** `coupled-target.ts:53–66,146–171` already uses positive tridiagonal elimination and implicit conduction; its dominant repeated work includes energy-path/stopping quadrature and three candidate steps per adaptive error estimate (`:225`). GPU/parallel sparse linear algebra is an inappropriate first optimization for tens of cells. First profile stopping evaluations, allocations and rejected steps in qualified cases. Compare the identical semi-discrete system against a SciML stiff integrator only if the measured cost/accuracy or parameter-sensitivity question warrants that independent oracle. [SciML method choices](https://docs.sciml.ai/DiffEqDocs/stable/solvers/ode_solve/) do not promise positivity or the project's discrete invariants automatically.
2. **Full-3V collision research:** `GENERAL3D-TOOLS-V17.md:14–35,90–120` traces entropy/cubature within Newton–Krylov residuals and quadratic pair work, with a proposed local Gaussian rule still requiring qualification. Browser worker pooling does not solve native high-dimensional quadrature scaling. Retain PETSc for a genuinely different velocity-space discretization and WarpX for particle references. Any tree/NUFFT/GPU acceleration must first pass the same entropy-gradient, adjoint/null-space, full-PDF, physical-rate and refinement gates. Do not replace a drifted/anisotropic problem with an isotropic closure just for speed.
3. **Collision transport:** v38 records old alignment/orientation execution remaining unsupported and continuum-bias status UNKNOWN (`COLLISION-QUALIFICATION-V38.md:13–28`). A high-resolution historical run does not qualify an interactive case. The next benchmark must be chosen inside a defensible physical envelope and compare actual transport observables; more seed replicas only tighten stochastic error. Keep solver agreement, numerical convergence and model validity separate.
4. **Plotting:** retain current SVG sample/keyboard interaction and baseline mechanism unless actual dense heatmap/linked-brush or frame-time requirements justify a measured library prototype. No evidence from current trace counts establishes that uPlot/Plotly is the missing accuracy tool. A switch must preserve exact values, units, uncertainty bands, keyboard/touch inspection and export.
5. **Rendering:** current field batching and on-demand apparatus rendering are good existing-tool use. The immediate issue is renderer lifetime (T42-2), not lack of postprocessing or a new CAD engine. Dimensioned CAD becomes valuable when sourced geometry/manufacturing constraints exist; it cannot supply unknown construction dimensions.
